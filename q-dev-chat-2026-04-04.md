question, i have a game which do steps like splash screen, loading, shopping ads, login, otp, switch to worldmap, and land on city, but it depends on network latency, so my current timing sometimes works and sometimes is off, what would be the best strategy to determine which stage is on to act accordingly

---

The best strategy is **state detection instead of fixed timeouts**. Rather than guessing how long each stage takes, you detect what's currently on screen and react to it.

**Current approach (fragile):**
```
wait 60s → assume splash done
wait 25s → assume Unity loaded
wait 10s → assume ads gone
```

**Better approach — state machine:**

```
detect current state → act → detect next state → act → ...
```

You already have OpenCV template matching — use it to build a state detector that runs in a loop and identifies which screen is currently showing:

```js
async function detectCurrentState(screenshotBuffer) {
  const [splash, loading, closeBtn, loginInput, canvas] = await Promise.all([
    this.imageProcessor.detectSplashLoading(screenshotBuffer),
    this.imageProcessor.detectLoading(screenshotBuffer),
    this.imageProcessor.detectCloseButton(screenshotBuffer),
    this.page.getByRole('textbox', { name: 'E-mail' }).isVisible({ timeout: 500 }).catch(() => false),
    this.page.locator('canvas').isVisible({ timeout: 500 }).catch(() => false)
  ])

  if (splash.found)      return 'SPLASH'
  if (loginInput)        return 'LOGIN'
  if (loading.found)     return 'LOADING'
  if (closeBtn.found)    return 'ADS'
  if (canvas)            return 'GAME'
  return 'UNKNOWN'
}
```

Then replace the sequential waits with a state machine loop:

```js
async function waitForState(targetState, timeout = 120000) {
  const start = Date.now()
  while (Date.now() - start < timeout) {
    const screenshot = await this.screenshot()
    const state = await this.detectCurrentState(screenshot)
    console.log(`[${this.config.workerId}] State: ${state}`)

    switch (state) {
      case 'SPLASH':
        await this.page.waitForTimeout(1000)
        break
      case 'LOGIN':
        if (targetState === 'LOGIN') return state
        await this.handleLogin()
        break
      case 'LOADING':
        await this.page.waitForTimeout(1000)
        break
      case 'ADS':
        await this.page.keyboard.press('Escape')
        await this.page.waitForTimeout(500)
        break
      case 'GAME':
        if (targetState === 'GAME') return state
        break
    }

    if (state === targetState) return state
    await this.page.waitForTimeout(500)
  }
  throw new Error(`Timeout waiting for state: ${targetState}`)
}
```

Then `initialize()` becomes:

```js

await this.openWorldMap()
await this.zoomingIn()
```

- Works on any network speed — fast or slow
- Self-healing — if an unexpected screen appears it handles it
- No more magic numbers like `waitForTimeout(25000)`
- Easy to add new states (OTP, verify account, etc.)

```js
function buildTileRequest(tiles, sessionToken, viewX, viewY) {
  // Each tile entry: 91 CF [x*1000+y as uint32 LE] [kingdom as uint32 LE]
  const tileBytes = []
  for (const { k, x, y } of tiles) {
    const tileId = x * 1000 + y
    tileBytes.push(0x91, 0xCF)
    tileBytes.push(tileId & 0xFF, (tileId >> 8) & 0xFF, (tileId >> 16) & 0xFF, (tileId >> 24) & 0xFF)
    tileBytes.push(k & 0xFF, (k >> 8) & 0xFF, (k >> 16) & 0xFF, (k >> 24) & 0xFF)
  }

  const playerList = Buffer.from([
    0x94,                          // fixarray[4]
    0xCD, viewX & 0xFF, (viewX >> 8) & 0xFF,  // field1
    0xCD, viewY & 0xFF, (viewY >> 8) & 0xFF,  // field2
    0x92,                          // fixarray[2]
    ...tileBytes,
    0xC4, 0x0C, ...sessionToken    // session token
  ])

  const header = Buffer.alloc(8)
  header.writeUInt32LE(playerList.length + 8, 0)
  header.writeUInt32LE(playerList.length, 4)

  return Buffer.concat([header, playerList])
}
```

Yes, exactly. The server uses a **cache/delta system** — it only returns data for tiles that have changed since the last time you requested them. If the game already has the tile data cached client-side, the server returns an empty response because nothing has changed.

This is why:
- The working requests you captured returned `tb:` data — those were tiles the game was loading for the first time
- Your scan of 836,624 returns empty — the game already has that tile cached

The server tracks what each session has already seen. The session token (`69 D1 4A 76...`) is tied to this cache state.

**This is a fundamental problem for your approach** — you can't just replay requests with the same token and expect fresh data, because the server thinks you already have it.

**What the game actually does:**
- Moves the map → requests only the newly visible tiles (not the ones already in view)
- The server returns data only for tiles not yet seen in this session

**Solutions:**

**Option 1 — Use a fresh token per scan batch**
Each time Playwright navigates to a new area, a new request is made with the current session token. Intercept that request, extract the token, and use it immediately before the server marks those tiles as "seen". This is essentially what the `TileScanner` in `browser-handler.js` already does.

**Option 2 — Force cache invalidation**
Navigate Playwright to a completely different area first, then back — this forces the server to resend tile data. But this defeats the purpose of bypassing Playwright.

**Option 3 — Use multiple sessions**
Each game account has its own cache state. With 6 workers each having their own session token, each worker can scan different tiles without cache conflicts. This is actually your current architecture — it already works correctly.

**The real takeaway:**
The direct HTTP approach works, but only for tiles that are **new to that session**. The best use is:
- Playwright navigates to a new area → intercepts the POST request → extracts fresh tile data from the response
- No need to make additional HTTP requests — just parse what the game already fetched

This is actually faster than making separate HTTP requests because you're piggy-backing on the game's own navigation. The `TileScanner.captureFromRequest` approach in `browser-handler.js` is the right direction — capture the session token AND parse the response data directly from the game's own requests.

```js
window.importCaptures = (json) => {
  try {
    const data = typeof json === 'string' ? JSON.parse(json) : json
```

Or merge with existing instead of overwriting:

```js
window.importCaptures = (json) => {
  try {
    const incoming = typeof json === 'string' ? JSON.parse(json) : json
    const existing = JSON.parse(localStorage.getItem('captured_coords') || '{}')
    const merged = { ...existing, ...incoming }
    localStorage.setItem('captured_coords', JSON.stringify(merged))
    console.log('✅ Merged:', Object.keys(incoming).length, 'incoming +', Object.keys(existing).length, 'existing =', Object.keys(merged).length, 'total')
  } catch (e) {
    console.error('Invalid JSON:', e.message)
  }
}
```
